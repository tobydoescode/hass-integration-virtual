# Virtual Home Assistant Integration Design

## Context

This repository will contain a HACS/manual Home Assistant custom integration for
creating virtual devices and entities for testing purposes. The integration will
live under `custom_components/virtual`.

The repository currently starts from a minimal README. The development and test
tooling should follow the existing local Kubernetes custom integration example
for devcontainer, Docker Compose, Taskfile, Python project metadata, linting,
testing, HACS metadata, CI, and Renovate configuration.

## Goals

- Provide a Home Assistant config flow for creating virtual devices.
- Allow each virtual device to contain zero or more switch entities.
- Allow switch entities to be added, edited, and removed after setup.
- Restore switch on/off state across Home Assistant restarts.
- Keep the data model stable enough for future YAML import/reload support.
- Include local development, test, HACS, CI, and dependency update tooling.

## Non-Goals

- YAML configuration or YAML reload support in v1.
- Entity types other than switches in v1.
- A single manager config entry that owns many virtual devices.
- Live file watching for declarative definitions.
- Editing virtual device IDs or switch keys after creation.

## Architecture

The integration will use one Home Assistant config entry per virtual device.
The `virtual` integration will forward config entries to the `switch` platform
only in v1.

Each config entry stores durable definitions:

- Device name.
- Virtual device ID.
- Optional device connection definition.
- Switch definitions.

Runtime switch state is not stored in config entry data. Switch entities use
Home Assistant restore state so their on/off values survive restarts and reloads.

The config entry data should remain declarative and import-friendly so a future
YAML feature can create or update the same structures without changing the
integration's internal model.

## Device Model

Each virtual device has:

- `name`: display name.
- `device_id`: stable device identity.
- `connection`: one optional connection definition.
- `switches`: list of switch definitions.

The `device_id` is generated by default using a UUID-backed value. Users may
specify it during initial setup when they need deterministic grouping or future
import behavior. The `device_id` is immutable after creation.

Device registry grouping always includes the integration-owned identifier:

```python
identifiers={(DOMAIN, device_id)}
```

The device may also include one connection. The connection type is one of:

- `none`: emit no connection.
- `mac`: emit a network MAC connection.
- `custom`: emit a user-specified connection type and value.

The internal data shape should allow changing this to multiple connections later
without requiring a major migration, but v1 exposes exactly one connection.

## Switch Model

Each switch has:

- `key`: stable unique key within the virtual device.
- `name`: display name.
- `icon`: optional Home Assistant icon string.
- `entity_category`: optional category, limited to blank, `config`, or
  `diagnostic`.
- `device_class`: optional switch device class selected from Home Assistant's
  known switch device classes.

Switch keys are generated from readable slugs by default, with suffixes added to
avoid collisions. Users may specify a key during switch creation. The key is
immutable after creation because changing it would create a new entity identity.

Each switch entity's unique ID is derived from the virtual device ID and switch
key. Each entity exposes `device_info` using the virtual device's identifier and
optional connection so all switches on the same virtual device are grouped under
the same Home Assistant device.

## Config Flow

Initial setup creates one virtual device.

The first step collects device details:

- Device name.
- Optional virtual device ID override.
- Connection type: `none`, `mac`, or `custom`.
- MAC address when connection type is `mac`.
- Custom connection type and connection value when connection type is `custom`.

The next step allows adding switches in a loop:

- Ask whether to add a switch.
- If yes, collect switch fields:
  - Name.
  - Optional key override.
  - Optional icon.
  - Optional entity category.
  - Optional switch device class.
- Repeat until the user finishes.

Empty devices are allowed. The config entry title is the device name.

Validation requirements:

- Reject duplicate virtual device IDs across existing config entries.
- Reject duplicate switch keys within the device.
- Validate required fields for the selected connection type.
- Normalize MAC addresses to lowercase colon-separated form before storing.

## Options Flow

The options flow is available from the existing virtual device config entry.

It supports:

- Editing device metadata:
  - Device name.
  - Connection type and value.
- Adding switches.
- Editing existing switches:
  - Name.
  - Icon.
  - Entity category.
  - Device class.
- Removing switches.

The virtual device ID and switch keys are immutable in the options flow.

Removing switches uses hard removal:

- The user selects one or more switches.
- The options flow shows an explicit confirmation step.
- The integration removes matching entity registry entries.
- The config entry data is updated.
- The integration reloads so removed entities disappear cleanly.

The integration registers a config entry update listener so options changes
reload the entry and refresh the platform state.

## Future YAML Support

YAML support is not part of v1. The v1 data model should still make it possible
to add later.

The likely future model is declarative YAML with a manual reload service:

- YAML definitions map to the same device and switch structures.
- Stable device IDs and switch keys identify existing objects.
- Reload creates, updates, and removes virtual definitions according to the
  YAML source of truth.

Live file watching is intentionally excluded from the v1 design and should not
be assumed by the data model.

## Repository Tooling

The repository should follow the local Kubernetes integration example for its
development and validation scaffolding.

Include:

- `custom_components/virtual` custom integration package.
- `.devcontainer/devcontainer.json` using
  `ghcr.io/home-assistant/devcontainer:2026.4`, forwarding port 8123, mounting
  `custom_components/virtual`, and running `uv sync --all-extras`.
- `docker-compose.yml` for running a local Home Assistant instance with the
  integration mounted read-only.
- `pyproject.toml` with project metadata, Ruff, pytest, and development
  dependencies.
- `Taskfile.yml` with `sync`, `lint`, `lint:fix`, `test`, `dev`, `dev:stop`,
  `dev:restart`, and `dev:logs`.
- `hacs.json`.
- `.pre-commit-config.yaml`.
- `.github/workflows/validate.yml`.
- `renovate.json`.

The devcontainer and Docker Compose setup are for personal development and
manual UI testing, not for maintaining a broad Home Assistant version support
matrix.

## Testing

Tests should cover:

- Config flow creation with generated IDs.
- Config flow creation with user-specified device IDs and switch keys.
- Empty virtual device creation.
- Connection validation and generated `device_info`.
- Duplicate virtual device ID validation.
- Duplicate switch key validation.
- Switch entity setup and unique IDs.
- Switch state restore behavior using Home Assistant's restore entity support.
- Options flow add switch.
- Options flow edit device metadata.
- Options flow edit switch metadata.
- Options flow hard-remove switch and entity registry cleanup.
- Config entry reload behavior after options updates.

## Open Implementation Notes

- Prefer Home Assistant enums/constants where available rather than hard-coded
  values, especially for switch device classes and entity categories.
- Keep the switch platform structure ready for additional entity types later by
  isolating shared device/entity definition helpers from switch-specific entity
  behavior.
- Avoid custom state persistence because Home Assistant already provides restore
  state for entities.
